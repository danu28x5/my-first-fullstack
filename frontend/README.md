# Notes App — Frontend

A Vite + React 19 single-page app backed by Supabase Auth and Postgres. Users can sign up, sign in, and manage their own private notes. Row-Level Security enforced at the database ensures users can never read or write each other's data — even if the client-side code is bypassed.

---

## Getting started

```bash
# from the repo root — start Supabase local stack first
cd supabase
supabase start
supabase db reset          # applies migrations + seed data

# then start the frontend
cd ../frontend
npm install
npm run dev                # http://localhost:5173
```

## Architecture

### Auth flow

Supabase Auth manages credentials. The `supabase.auth.onAuthStateChange` listener in `App.jsx` is the single source of truth for authentication state. It fires immediately with the current session on mount, and again whenever the session changes (sign-in, sign-out, token refresh).

Session state uses three values:

| Value | Meaning |
|---|---|
| `undefined` | Still loading — waiting for `getSession()` to resolve |
| `null` | Signed out |
| `Session` object | Signed in |

This avoids needing a separate `isLoading` boolean in state. Instead, `isLoading` is derived from `session === undefined` during render (see *Skill rules* below).

### Sign-up and profile creation

When a user signs up, `AuthForm` calls `supabase.auth.signUp`, then inserts a row into `public.users` with the new `auth.uid()` as the primary key. The `public.users` table has a foreign key referencing `auth.users(id)`, so the auth record must be created first.

A `23505` (unique_violation) conflict code from the profile insert is silently ignored — it means the profile already exists (e.g., from the seed data).

### Notes and RLS

The `public.notes` table has Row-Level Security enabled and forced. The policies are:

- **SELECT** — `(select auth.uid()) = user_id`
- **INSERT** — `with check ((select auth.uid()) = user_id)`
- **UPDATE** — both `using` and `with check` clauses
- **DELETE** — `using ((select auth.uid()) = user_id)`

Because RLS is enforced at the database level, `NoteList` can issue a plain `select * from notes` — Postgres automatically filters to only the calling user's rows. There is no `where user_id = ...` clause needed in the client query.

### No client-side router

The app has exactly two views: the auth form and the notes dashboard. A router would add bundle weight and complexity for no benefit at this scope. Conditional rendering based on `session` state is sufficient and keeps the bundle small.

## Database types

`src/database.types.ts` is generated from the live local Supabase schema:

```bash
# from the supabase/ directory
supabase gen types typescript --local > ../frontend/src/database.types.ts
```

`src/lib/supabase.ts` passes the `Database` type to `createClient<Database>`, giving the Supabase client full TypeScript awareness of table names, column types, and insert/update shapes. It also re-exports convenience aliases so components import from the lib file rather than the generated file directly.

## Skill rules applied

The following Vercel React performance rules were applied throughout this codebase.

### `bundle-barrel-imports` (CRITICAL)

All imports are direct — from the exact source file, not from a barrel `index.js`. This prevents loading unused modules and keeps dev boot times fast.

```js
// Correct: direct source imports
import { supabase } from './lib/supabase'
import AuthForm from './components/AuthForm'
import NoteList from './components/NoteList'
```

No `index.js` barrel files were created in `components/` or `lib/`.

### `rerender-no-inline-components` (HIGH)

Every component (`AuthForm`, `NoteCard`, `NoteEditor`, `NoteList`) is defined at module top level — never inside another component. Defining a component inside a render function creates a new component *type* on every render, causing React to fully unmount and remount it (losing all internal state, re-running effects, recreating DOM nodes).

### `rerender-derived-state-no-effect` (MEDIUM)

Values that can be computed from existing state are computed during render — they are not stored as additional state, and they are never updated in a `useEffect`.

Examples:
- `App.jsx`: `const isLoading = session === undefined` — derived from session, not stored
- `AuthForm.jsx`: `const isSignUp = mode === 'signup'`, `const submitLabel = ...`, `const toggleLabel = ...` — all derived from the `mode` state during render
- `NoteCard.jsx`: `const formattedDate = new Date(note.updated_at).toLocaleDateString(...)` — derived from the `note` prop
- `NoteList.jsx`: `const isEditorOpen = editingNote !== null` — derived from `editingNote` state
- `NoteEditor.jsx`: `const isEditing = initial !== null`, `const heading = ...`, `const saveLabel = ...`

### `rendering-conditional-render` (prevents rendering incorrect values)

Ternary operators (`? :`) are used for all conditional rendering — never `&&` — because `&&` renders falsy values like `0`, `NaN`, or `null` as text when the left side is not strictly boolean.

```jsx
// Correct: ternary prevents rendering "null" text
{note.content !== null ? (
  <p className="note-card-content">{note.content}</p>
) : null}

{error !== null ? (
  <p className="auth-error" role="alert">{error}</p>
) : null}
```

### `rerender-functional-setstate` (MEDIUM)

All state updater calls in CRUD callbacks use the functional form `setState(curr => ...)`. This ensures callbacks always operate on the *latest* state value, not a stale snapshot captured in a closure — and allows the callbacks to omit state from their dependency arrays.

```js
// Correct: functional setState — no stale closure risk
setNotes(curr => [data, ...curr])           // after create
setNotes(curr => curr.map(n => n.id === data.id ? data : n))  // after update
setNotes(curr => curr.filter(n => n.id !== id))               // after delete
```

## Environment variables

Defined in `frontend/.env.local` (not committed to source control):

| Variable | Purpose |
|---|---|
| `VITE_SUPABASE_URL` | Supabase project URL (local: `http://localhost:54321`) |
| `VITE_SUPABASE_ANON_KEY` | Public anon key — safe to expose to the browser |

Vite only exposes variables prefixed `VITE_` to client-side code. The anon key is intentionally public; it only grants access subject to your RLS policies.
